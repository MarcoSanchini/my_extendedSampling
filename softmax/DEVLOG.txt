================================================================================
DEVLOG -- gradient/HMC-informed rate sampler for sequence space
================================================================================
Living record of what was tried, what worked, what didn't, and why, across
the various implementations of classes/rate_sampler.py:ExtendedProteinRateSampler.
Update this file (append, don't rewrite history) whenever the design changes
or a test reveals something that changes the plan. Newest entries at the
bottom of the file.

Context: the existing classes/ep_sampler.py:ExtendedProteinSampler does HMC
in the continuous (softmax-relaxed) sequence space, using `isteps` (default
100) leapfrog integration steps per Monte Carlo move before collapsing to a
discrete sequence and doing a single Metropolis accept/reject. That's slow.
The goal of this sampler is to replace the many-small-steps trajectory with
a single gradient-informed jump per move, using an explicit rate/Hastings
correction (since a one-shot discretized jump, unlike a full leapfrog
trajectory, isn't automatically reversible/volume-preserving) so the target
distribution stays exp(-U/T) exactly.

================================================================================
2026-09-17 -- initial derivation
================================================================================
Starting point: sequence represented per-site as one-hot logits (mean-
centered, gauge-fixing the softmax translation invariance). One leapfrog
half-step gives:
    delta_x_i = dt*p_i/m_i - dt^2/(2m_i)*grad_i(U)|_A
with p_i ~ N(0, m_i*T) (HMC momentum). This makes delta_x_i Gaussian:
    delta_x_i ~ N(-dt^2/(2m_i)*grad_i(U), dt^2*T/m_i)
-- confirmed this matches classes/ep_sampler.py's leapfrog position update
exactly (one HMC leapfrog step with fresh momentum == one MALA/Langevin
step, standard result).

Proposed reading off, per site, which amino acid e_j the noisy displacement
"points at" (component x_j is the largest among competitors), and using a
locally-balanced/Zanella-style rate:
    r_ij = a_ij * min(1, exp(-dU_ji/T) * a_ji/a_ij)
Verified this satisfies detailed balance: pi_i*r_ij = min(pi_i*a_ij,
pi_j*a_ji) = pi_j*r_ji, the standard Metropolis-rate construction (same
family as Zanella 2020 locally-balanced proposals / Gibbs-With-Gradients /
Path-Auxiliary samplers).

Original a_ij definition: "pointing at e_j" means x_j > x_k for every k
!= i,j (i = current site, j = candidate target; i itself excluded from the
comparison, since it represents "not moving"). Derived a closed form:
    a_ij = integral f_{0,1}(u) * prod_{k!=i,j} Phi(alpha_kj + beta_kj*u) du
    alpha_kj = (mu_j - mu_k)/sigma_k,  beta_kj = sigma_j/sigma_k
(corrected a subscript error in an intermediate derivation: alpha_kj's
denominator is sigma_k, the std of the competitor being compared against,
not sigma_j). Confirmed this is the correct "independent, non-identical
Gaussian is the max" formula, and noted it's a Thurstone/probit choice
model when sigma is constant across classes (which it is here, since dt/T/M
are global scalars) -- the probit analogue of the softmax-based proposal
used in Gibbs-With-Gradients.

Flagged design risks at this stage (before any code): (1) exact detailed
balance requires the REVERSE proposal probability a_ji to be evaluated
using the gradient AT the proposed point B, not reused from A -- an
approximation either way trades exactness for cost; (2) the mean-centering
gauge-fix technically correlates the K components of the noise (pairwise
correlation -1/(K-1)), so treating them as independent (as the closed form
above does) is a deliberate, small approximation, not exact; (3) a single
gradient at A is only a first-order approximation of the effect of a large
(non-infinitesimal) discrete jump -- U_am runs through several nonlinear
self-attention layers, so this could be a poor approximation (this turned
out to be the central issue investigated over the following days).

2026-09-17/18 -- repo setup, first implementation (JOINT multi-site design)
================================================================================
Found the existing codebase: classes/ep_sampler.py (the leapfrog HMC
sampler), utils/energies.py:compute_U_am (squared log-diff of attention
maps between current and reference sequence, upper-triangular sum), and the
customs/custom_esm package providing ESM3.predict_attention(sequence_probs)
-- a differentiable forward pass through the real attention computation,
confirmed end-to-end differentiable via customs/differentiability.txt (a
real gradient log: finite, well-scaled, SoftmaxBackward0 in the graph).

Implemented:
  - utils/proposals.py: log_pointing_prob(mu, sigma, target, n_nodes) --
    Gauss-Hermite quadrature evaluation of the a_ij formula. Independently
    validated in a scratchpad (numpy/scipy, since no torch was available in
    the sandbox) against brute-force Monte Carlo across K=3..25 and a range
    of gradient scales: exact normalization, agreement with MC within
    noise, and quadrature converged to ~6 significant figures by 20 nodes
    even in the steepest case tested (n_quad=40 default judged safe).
  - classes/rate_sampler.py (v1, JOINT design): every site simultaneously
    drew a displacement and voted (via a K-way argmax competition that
    included "stay" as one of the K classes, after an earlier version's
    bug where excluding "stay" forced every site to propose a change every
    move -- fixed by including the current class in the competition on
    equal footing) on whether/what to change to; the whole joint candidate
    was accepted/rejected with the true joint dU and the true reverse
    probability (using a second backward pass at the candidate B).
  - tests/test_proposals.py, tests/test_steepest_descent.py,
    tests/test_joint_coupling.py (see below), monte_carlo/main_rate.py +
    rate_inputs/.

Bug found via tests/test_steepest_descent.py (real model run): the
gradient-informed direction sometimes pointed at 'X' (and could point at
B/U/Z/O), the ambiguity/non-standard residue codes at the tail of
SEQUENCE_USED_VOCAB -- even when doing so INCREASED the true energy
relative to staying. Fixed by permanently excluding these 5 codes from the
competition (classes/rate_sampler.py:_NONCANONICAL_RESIDUES, a large but
FINITE penalty so a site already sitting on one of these codes doesn't
produce nan in log_pointing_prob). This measurably improved things (top-1
accuracy and mean dU both improved) but did not fix the deeper problem
below.

tests/test_steepest_descent.py (after the X fix) still showed the gradient
badly mispredicting the true single-site optimum: top-1 accuracy 1/10,
and critically 4/10 sites showed the gradient confidently predicting "stay"
(dU=+0.0000) while a large true improvement (dU -20 to -27) sat one hop
away, completely invisible to the gradient.

Built tests/test_steepest_descent.py's "exploration budget" extension:
swept dt (reusing the already-computed gradient, no new ESM3 calls) and
found a[best] pinned at ~1/K (uniform) across the ENTIRE dt range tested
(0.5 to 20, then widened to 1600), for every one of the 10 tested sites,
including ones with clear deterministic (p=0) preference. Traced this to
the actual gradient gaps at these sites being tiny (~0.02), implying
(via alpha ~ dt*grad_gap/(2*sqrt(M*T))) that dt~400 would be needed for
real concentration at T=20 -- two orders of magnitude past what was tested.

Real run with the widened sweep (dt 0.5..1600) gave a different, more
important result than expected: for 4 of 10 sites, INCREASING dt made
finding the true best MORE unlikely (a[best] -> 0, E[#moves to hit it] ->
literal inf), not less -- the local gradient at those sites is not just
uninformative, it's confidently WRONG (favors staying when a large true
improvement exists elsewhere). No dt fixes this; it strictly worsens with
dt at those specific sites. For the sites where dt did help, it only
helped modestly (E[#moves] ~20 -> ~12 even at dt=1600, an already
impractical step size), and 2 of those sites were non-monotonic (a[best]
rises then falls past a certain dt, because the gradient's true favorite
isn't the global true-best class).

tests/test_joint_coupling.py: built to test the user's hypothesis that the
single-site brute-force ground truth (test_steepest_descent.py, holding
every OTHER site fixed at the CURRENT sequence) might not be a fair proxy
for the sampler, since it proposes MANY sites changing simultaneously and
U_am (through self-attention) need not be separable across sites. Decomposed
real joint moves into sum_linear (first-order Taylor, no coupling),
sum_isolated (true single-site effects applied one at a time, still no
coupling), and dU_joint (true effect with all analyzed sites changed at
once). Result: coupling (dU_joint - sum_isolated) was frequently AS LARGE
OR LARGER than the within-site nonlinearity term, e.g. one trial:
sum_isolated=-16.5 (mildly favorable) but dU_joint=+401.2 (strongly
unfavorable) for the same 15-site move. U is strongly non-separable across
simultaneously-changed sites for this energy.

Combined with a critical, simpler fact from the same runs: EVERY trial
across dt=1e-5 to dt=1600 touched ~51-56 of 58 sites simultaneously. At
T=20, a dU of +500 to +1000 (routinely observed) means essentially exactly
zero acceptance probability. The joint design was, in practice, proposing
to rewrite almost the entire sequence every move and being rejected nearly
always.

Root cause identified (not just "needs more tuning"): the K-way-including-
stay competition has NO small-dt limit that favors staying. Since mu ~
dt^2 and sigma ~ dt, their ratio (which is all that matters for the argmax
outcome) -> dt -> 0 as dt -> 0, giving a UNIFORM competition (each of K
classes ~1/K), not a stay-concentrated one -- unlike a true continuous
Langevin/MALA step, which naturally stays close to its starting point at
small step size because it never has to make a discrete argmax decision.
Nothing in delta_x = dt*momentum/M - step_coef*grad references the CURRENT
identity at all; "stay" only wins by having a favorable relative mu, which
requires a large dt exactly where coupling then destroys the move. There is
no dt that gives "few sites change, and the few that do are well chosen."

Side investigation (sum_linear consistently small-but-positive across 18
independent trials, spanning 5 orders of magnitude in dt): resolved, not a
bug. Two combined reasons: (1) at low dt the target is chosen by momentum
noise, not the gradient, so no per-site "descent" guarantee holds; (2) the
test sequence (5 random mutations from REF_SEQ) is IDENTICAL to the
reference at 53 of 58 positions (verified directly: differing positions
are 5, 17, 33, 36, 55), and U_am is by definition minimized at the
reference -- so those 53 positions are already at/near a local optimum,
and a broad, largely-random perturbation away from a mostly-already-good
sequence is expected, on average and to first order, to increase U. This
is the model behaving sensibly, not a red flag, and it gives a good
sanity check for the next version: proposals landing on one of the 5
genuinely-suboptimal sites should have a much higher acceptance rate than
proposals landing on one of the 53 reference-matching sites.

A secondary, more technical point was raised in the same discussion and is
worth keeping in mind (not yet acted on): grad_A is d(U)/d(logits), not
d(U)/d(probs), and because softmax is translation-invariant, d(U)/d(logits)
sums to exactly zero across the K classes at every site. That makes the
"current" class's component an aggregate/residual quantity (= -sum of all
other classes' components), not a component on the same independent
footing as any single "other" class -- so comparing grad[cur] against
grad[some specific other class] directly (as the joint design's K-way
competition did) is not quite the clean two-point comparison it looks
like. Did not end up mattering for the diagnosis above (which was driven
by the coupling/all-sites-touched finding), but worth remembering if
calibration issues resurface.

2026-09-19 -- pivot to single-site-per-move (M=1)
================================================================================
Decision: fix "how many sites change per move" directly instead of trying
to control it indirectly via dt/T (which the evidence above shows doesn't
work -- dt/T controls confidence, not headcount, and the headcount is
dominated by how many sites have ANY directional preference at all, which
was found to be most of them). Simplest, safest choice: exactly one site
per move (M=1), chosen uniformly at random -- uniform selection is
state-independent, so its probability is identical forward and backward
and cancels exactly out of the Hastings ratio, no correction term needed.
This removes the coupling failure mode by construction: with only one site
changing, there's nothing for it to couple with.

Considered and rejected (for now) two alternatives:
  - Bernoulli(p) per site independently (variable number of sites touched,
    Binomial(L,p)/~Poisson(L*p) distributed): correctness is fine (same
    cancellation argument as uniform single-site), but it reintroduces a
    fat-tailed, uncontrolled version of exactly the risk just fixed (~1-in-4
    moves would touch 2+ sites simultaneously at E[N]=1, and we don't yet
    know how fast coupling degrades between N=1 and the already-measured
    catastrophic N~54), plus wastes ~37% of moves on N=0 identity moves
    that M=1 never produces. Worth revisiting once a real N-sweep
    (extending test_joint_coupling.py's method to a few small FIXED N
    instead of dt) maps out the coupling-vs-N curve.
  - Informed (gradient-weighted) site selection: valid in principle (needs
    an extra q(s|B)/q(s|A) term using grad_B, which is already computed for
    the reverse pass, so not a new ESM3 call) but deferred until the
    uniform version is validated, since it also needs a first, cheap,
    whole-sequence pass to rank sites before the expensive single-site
    relaxed gradient -- premature complexity before knowing if M=1 alone is
    enough.

Direction-choice, given a site is chosen: returned to the ORIGINAL formula
from the initial derivation (2026-09-17 section above) -- product over
k != i,j, i.e. "stay" (i) is excluded from the competition entirely, not
included as in the (now superseded) joint design. This is the natural
formulation once site selection is a separate, prior step: having already
committed to changing this site, "stay" isn't a candidate any more, only
which OTHER amino acid to move to is. Implemented via the same
large-finite-penalty masking trick already used for the non-canonical
residues (classes/rate_sampler.py:_penalize_indices, now also given the
site's current index), which was verified numerically to exactly reproduce
P(x_j > x_k for all k != i,j) against direct Monte Carlo restricted to the
K-1 classes excluding i (i is never sampled at all, not discarded after
the fact) -- see tests/test_proposals.py:check_exclusion_masking.

Gradient computation also changed: instead of relaxing the WHOLE sequence
through softmax(logits/T_sftm) and reading off one site's row of a big
(L,K) gradient (as the joint design did), the new _grad_pass_site relaxes
ONLY the one chosen site; every other site is held at its exact discrete
(hard one-hot) value. This costs the same (attention/embedding cost does
not depend on how many positions are soft vs hard -- a hard one-hot is
just a degenerate probability row through the same embedding lookup) and
is a more faithful partial derivative: it matches the exact discrete
context used everywhere else (the exact-dU forward pass, the reverse-
probability pass), rather than evaluating the gradient with every other
site also slightly blurred by T_sftm.

Old joint-design test files (tests/test_steepest_descent.py and
tests/test_joint_coupling.py) moved to tests/archive/*_JOINT_DESIGN.py,
each annotated with why they were superseded; their findings are the
2026-09-17/18 section above. New tests/test_steepest_descent.py rebuilt
for the single-site design: same p=0 (mu_A . grad_A <= 0) construction
check, plus the true-best brute-force comparison, now correctly excluding
"stay" from both the prediction and the candidate set (matching what
_step() can actually propose).

Status at time of writing: implementation complete
(classes/rate_sampler.py rewritten, tests updated/added), NOT YET RUN
against the real model (no torch/ESM3/weights available in this sandbox --
same limitation as every prior round; static review + independent math
validation only). Next: run tests/test_proposals.py (pure torch, cheap)
and tests/test_steepest_descent.py (live model) to confirm the single-site
version behaves as expected before a real monte_carlo/main_rate.py run.
Open question to check once real numbers are in: does dt need retuning
now that it only controls one site's competition sharpness rather than
global coupling risk (raising it should now be safe in a way it wasn't
before, since there's no longer a "too many sites at once" failure mode)?

2026-09-21 -- real run: single-site design, gradient relaxation check
--------------------------------------------------------------------------------
tests/test_proposals.py: all checks passed against the real torch build,
including the new check_exclusion_masking (a[excluded]=0.00e+00 at every K
tested) -- confirms the exclude-i-and-j masking trick is exact in practice,

tests/test_steepest_descent.py (single-site, _grad_pass_site): top-1
accuracy improved slightly vs. the last joint-design run (2/10 vs 1/10).
One result looked alarming at first: site 4's gradient-predicted
substitution had a true dU of +356.5, far larger in magnitude than
anything seen in any previous test (worst previously ~-93), which dragged
the headline "mean dU at predicted" to +17.2 (looks like the prediction is
now worse than random). Checked this specifically: excluding that single
outlier, the other 9 sites averaged dU~-20.5, nearly identical to the
-21.5 seen before the _grad_pass_site change -- so the aggregate mean was
being dominated by one point in a small (N=10) sample, not a real
regression.

Built tests/compare_grad_methods.py to isolate whether that outlier was a
genuine property of site 4 or an artifact of relaxing only one site
(_grad_pass_site) instead of the whole sequence (the older, removed
_grad_pass). Result: cosine similarity between the two gradient methods
was >=0.9995 (effectively +1.0000) at every one of the 10 tested sites,
including site 4, and both methods picked the exact same substitution at
every site. The two methods agree almost perfectly in direction; they only
differ slightly in magnitude. Conclusion: the site-4 outlier is a real,
if extreme, instance of the known linearization-quality limit (the local
gradient is confidently wrong there) -- not a bug or an artifact introduced
by the site-only relaxation. _grad_pass_site is validated as behaving
equivalently to the (more expensive, less faithful-in-context) whole-
sequence method it replaced, while being strictly more faithful to the
exact discrete context used everywhere else. No further action needed on
the gradient computation itself.

Status: single-site design considered validated at the unit/diagnostic
level (math checks, p=0 construction check, brute-force single-site
comparison, gradient-method cross-check). Next: an actual
monte_carlo/main_rate.py run, to see real acc_rate and whether U trends
down over many moves -- the thing none of the diagnostics so far can
actually tell us, since they all evaluate one proposed move at a time
against a fixed starting sequence rather than a moving chain.

2026-09-21 -- first real main_rate.py run: device-mismatch bug, fixed
--------------------------------------------------------------------------------
First real monte_carlo/main_rate.py run (GPU, cuda:0) crashed on move 1:
    RuntimeError: Expected all tensors to be on the same device, but got
    tensors is on cuda:0, different from other tensors on cpu
    (classes/rate_sampler.py:_step, the excl_A = torch.unique(torch.cat(...))
    line).

Cause: self._noncanonical_idx is built in _init_attributes() (called from
__init__, before any device is known) via a plain torch.tensor(...), which
defaults to CPU. _step concatenates it directly with cur_idx/tgt_idx (which
live on eprot.device, cuda:0 on a GPU run) via torch.cat, which requires
matching devices -- crash. This was NOT caught by
tests/test_steepest_descent.py or tests/compare_grad_methods.py, run
earlier on the same GPU machine, because those scripts build their
exclusion sets from plain Python ints (via .item()) into fresh CPU tensors
rather than reusing the device-carrying cur_idx/tgt_idx tensors directly --
so they happened to sidestep the bug rather than exercise the code path
that has it. A reminder that a diagnostic script that reimplements a piece
of logic instead of calling the real method under test can pass while the
real method still has a bug.

Fix: move self._noncanonical_idx onto settings["device"] once inside
_setup(), right after that device is fully resolved (string -> torch.device,
with the cuda-unavailable -> cpu fallback already applied) and before it's
used anywhere. _penalize_indices() already had a per-call .to(x.device) as
a second line of defense, which is why only the raw torch.cat calls in
_step (before _penalize_indices runs) were actually broken.

Also noted while looking at the run's output: rate_inputs/pars.txt's
default init_muts=0 means main_rate.py's starting sequence is the reference
itself (U=0 already, nothing to improve) unless changed -- everything
validated in this file so far (test_steepest_descent.py,
compare_grad_methods.py, the earlier joint-design diagnostics) used 5
random initial mutations instead. Recommended setting init_muts=5 to match
before drawing conclusions from a real run's acc_rate/U trend. Set to 5.

2026-09-21 -- first successful 500-move main_rate.py run (T=20, dt=2, seed=42)
--------------------------------------------------------------------------------
First real run to complete without crashing: 500 moves, init_muts=5 (4
actually changed the sequence vs reference -- one of the 5 random draws
coincidentally picked the residue already there), T=20, dt=2, results in
monte_carlo/tests_rate/sim0/.

Built monte_carlo/analyze_run.py (pure Python stdlib, no torch/numpy
needed) to analyze data.dat: reconstructs the initial sequence purely from
the log (for each site, cur_aa the first time it's touched records what
was there before any move touched it -- confirmed exactly against the
logged Hd_to_ref=4 at move 0), then reports U/Hd_to_ref trajectories in
blocks, windowed (not just cumulative) acceptance rate, dU stats split by
accepted/rejected, and the per-site accept-rate sanity check noted
earlier in this file (initially-mutated sites vs initially-reference-
matching sites).

Findings from the real run:
  - The accept/reject mechanics themselves are working correctly: rejected
    moves have mean dU=+128.4 (clearly bad), accepted moves have mean
    dU=+1.3 (near-neutral) -- a large, sensible separation. This is not a
    correctness problem.
  - But T=20 looks too hot for this design's move granularity (one hard
    substitution per move, dU routinely tens to hundreds, vs ep_sampler.py's
    many-small-leapfrog-steps-then-one-accept/reject, where T=20 was
    presumably tuned/inherited from). Symptoms: U never reached a stable
    plateau over 500 moves (61 -> peak ~341 around move 350-400 -> ~268 by
    move 500, still relaxing, not equilibrated); Hd_to_ref drifted from 4
    to 46 of 56 positions (the chain ended up almost entirely different
    from the reference, not staying near it); and the per-site accept-rate
    gap between initially-mutated (0.372) and initially-reference-matching
    (0.311) sites, while in the right direction, is weak -- consistent
    with a temperature too high to sharply discriminate between favorable
    and unfavorable substitutions at this energy scale.

Next: rerun with a substantially lower T (try T=1 or T=2) and compare --
does Hd_to_ref stabilize near the initial value instead of drifting away,
does U visibly plateau within the same move budget? Note T also enters
sigma=dt*sqrt(T/M) (the proposal's std), so lowering it should sharpen the
proposal too, as a side effect of the same physically-motivated parameter
rather than a second knob fighting the first.

2026-09-21/22 -- T=2, 5000-move run: equilibration fixed, drift/selectivity not
--------------------------------------------------------------------------------
Second run (tests_rate/sim1): T=2 (down from 20), dt=2 (unchanged), 5000
moves (up from 500), same init_muts=5/seed=42. Analyzed with
monte_carlo/analyze_run.py (user ran it independently and pushed the
output as sim1_T2.0_steps5000_muts5_results.txt -- good, the tool is
being used as intended).

Comparison to the T=20 run:
  - U: T=20 was still climbing without bound at move 500 (61->267, peak
    341, no plateau). T=2 reaches a rough plateau around 70-83 after
    move ~2000 -- lowering T fixed the equilibration problem.
  - accepted-move dU: T=20 mean +1.3, range [-68,+59]. T=2 mean +0.03,
    range [-12,+12] -- much tighter, as expected from a stricter Boltzmann
    filter at lower T.
  - Hd_to_ref: still drifted heavily either way (T=20: 4->46/56, T=2:
    4->48/56, over 10x more moves). Lowering T did not stop the drift.
  - mutated-site vs reference-matching-site accept rate: T=20 showed a
    real (if weak) gap, 0.372 vs 0.311. T=2 showed NO gap at all, 0.149 vs
    0.152 -- statistically indistinguishable. This is the important
    result: a colder T makes the accept/reject filter STRICTER but not
    SMARTER. It doesn't help the proposal preferentially find good
    substitutions at the genuinely-improvable sites; it just rejects more
    of everything roughly uniformly.

Diagnosis: this reconnects to the exploration-budget finding from
2026-09-17/18 above -- the standardized gap driving a site's proposal
choice scales as alpha ~ dt/sqrt(T), and at T=20 real concentration was
found to need dt in the hundreds (vs dt=2 used throughout every run so
far). Dropping T from 20 to 2 only buys back a factor of sqrt(10)~3.16 in
that ratio -- nowhere near enough to make the proposal actually informed.
So the sampler is currently behaving close to "propose a near-random
substitution at a uniformly random site, then filter by an increasingly
strict energy criterion" rather than "intelligently suggest good
substitutions" -- a stricter filter (lower T) stabilizes U but can't make
the proposal itself smarter, which is exactly why the site-type
selectivity gap flattened instead of sharpening.

Next: raise dt substantially (try dt=20, 50, 100) at the same T=2. This is
now safe to push hard on, unlike in the old joint-multi-site design --
there is no coupling-blowup risk from a large dt here, since only one site
changes per move regardless of how confidently it's chosen. Expected
signature of success: the accept rate at the 4 originally-mutated sites
should rise clearly ABOVE the reference-matching sites' rate (a real,
growing gap), since an actually gradient-informed proposal should more
often land on genuinely favorable substitutions there specifically, while
the reference-matching sites' rate should stay low and roughly flat (no
substitution is genuinely better than staying there, regardless of how
well-informed the proposal is -- their protection comes from the
accept/reject step, which is already confirmed working, not from the
proposal avoiding them).

2026-09-22 -- dt sweep (20/50/100/150, T=2): identical trajectories, not a bug
--------------------------------------------------------------------------------
Added monte_carlo/sweep_dt.sh (adapted from the user's ep_sampler.py
fixed-tau sweep template; GPU-parallel, MAX_RUNNING=4). Important
correctness fix made before trusting it: the sed override for T used
`s/^T[[:space:]]*.*/.../`, and since [[:space:]]* also matches zero
characters, ^T alone matches "T_sftm ..." too -- this would have silently
clobbered T_sftm on every sweep run. Fixed by requiring a real whitespace
boundary ([[:space:]] without the *) for all four overridden keys (dt, T,
moves, init_muts), and verified the actual sed substitutions against the
real rate_inputs/pars.txt and settings.txt before trusting it. Also:
each dt gets its own dedicated results_dir (tests_rate_sweep_dt/dt<DT>)
rather than sharing tests_rate/sim<N>'s auto-incrementing counter.txt (that
counter lives inside whatever raw_path is passed to find_path, so
simultaneous runs sharing one raw_path would race on it -- separate
raw_paths avoid that by construction).

First sweep: dt=(20,50,100,150), T=2, moves=5000, init_muts=5, seed=42.
Result looked like a null finding at first (U/Hd_to_ref/accept-rate
numbers nearly identical across all four dt) -- but checking the raw
data.dat rows directly showed the first ~8 moves are BIT-FOR-BIT IDENTICAL
across all four dt values, same site, same proposed_aa, same dU to the
last float digit (e.g. 53.16386795043945 exactly, in all four). Not a bug:
a provable consequence of the math. The argmax that picks the proposed
substitution only depends on p_k - (dt/2)*grad_k per class (the common
positive factor dt/M cancels out of any argmax comparison). Momentum p_k
has a dt-INDEPENDENT scale (~sqrt(T*M), drawn the same way regardless of
dt), while the gradient term grows only linearly with dt. With the tiny
gradient gaps measured earlier (~0.02), the crossover where the gradient
term starts to matter is dt* ~ 2*sqrt(T*M)/grad_gap ~ 2*sqrt(2)/0.02 ~ 141
at T=2 -- almost exactly dt=150, which is why that run showed only
marginal differences (a few site/momentum combinations happened to cross
the threshold) while dt=20/50/100 (well below it) reproduced the
momentum-only trajectory exactly.

Conclusion: none of dt=20/50/100/150 actually tested a meaningfully
gradient-informed proposal -- dt=150 sits right ON the marginal crossover,
not decisively past it. Updated sweep_dt.sh's default DTS to
(300, 600, 1000, 1300): several times past the crossover instead of
sitting on it, while staying under the point (roughly dt>1400 for typical
gradient magnitudes) where step_coef=dt^2/(2M) could start overwhelming
the fixed -1e6 exclusion penalty used to keep non-canonical residues and
the current amino acid out of the competition. Same expected signature of
success as before: the accept-rate gap between the 4 originally-mutated
sites and the 52 reference-matching sites should now actually open up if
gradient-informedness is the missing piece; if it still doesn't, that
would point at something else entirely (worth knowing either way).

2026-09-22 -- refactor: exclusion by slicing instead of penalty, before the dt=(300,600,1000,1300) sweep
--------------------------------------------------------------------------------
Prompted by a question about the previous sweep entry's own caveat above
(step_coef*grad could start overwhelming the fixed -1e6 exclusion penalty
around dt>1400): why penalize non-canonical residues and the current
amino acid at all, instead of just never letting them compete? The
per-site formula this sampler is built on is
P(delta_x_j = max_{k!=i,j} delta_x_k), a product over k != i,j from the
start -- "i" (current class) and non-canonical residues were never
supposed to be in the competition, so masking them with a large negative
constant was doing extra, riskier work to get the same result a smaller
candidate set gives for free.

Replaced the additive penalty with physical slicing in
classes/rate_sampler.py:
  - Removed module constant _EXCLUSION_PENALTY (-1.0e6) and the methods
    _penalize_indices / _penalize_noncanonical.
  - Renamed self._noncanonical_idx (indices of X/B/U/Z/O, set in
    _init_attributes, moved to settings["device"] in _setup after device
    resolution -- see the 2026-09-19-ish device-mismatch fix entry above)
    to self._canonical_idx: now stores the indices NOT in
    _NONCANONICAL_RESIDUES, i.e. the full candidate universe, computed
    once and reused every step.
  - New method _competition_indices(exclude_idx): returns
    self._canonical_idx with exclude_idx (typically the site's current
    amino acid) masked out -- a plain boolean-masked slice, no constant,
    no fixed-size tensor with penalized entries sitting in it.
  - _step() rewritten around this: mu_A/mu_B and delta_x are still
    computed over the FULL vocab (gauge-fixing delta_x -= delta_x.mean()
    still happens over the full space, before any slicing -- doing it
    after would change the fixed point), but the argmax that picks the
    proposed class, and both directions of log_pointing_prob (forward
    log_a_AB, reverse log_a_BA), now index into competitors_A /
    competitors_B, so log_pointing_prob only ever sees the reduced
    (K-1-or-fewer) canonical competitor set for that call, plus a
    local-index -> global-vocab-index mapping step. Also handles the edge
    case where the reverse move's target (cur, the original amino acid)
    is itself non-canonical: impossible for the CURRENT design since cur
    always comes from an ExtendedProtein's argmax over canonical-only
    proposals, but the code path (log_a_BA = -inf if cur is not found in
    competitors_B) is there defensively rather than assumed away.

Updated tests/test_steepest_descent.py and tests/compare_grad_methods.py
to call sampler._competition_indices(cur) and index into it (local argmax
-> global vocab index) instead of the removed
_penalize_indices/_noncanonical_idx calls. tests/test_proposals.py needed
no logic changes (check_exclusion_masking tests the general-purpose
penalty-masking trick inside utils/proposals.py:log_pointing_prob
directly, which is still correct, general code -- just no longer what the
sampler itself calls); only its docstring and the __main__ banner were
updated so they don't misdescribe current production behavior.

All four files verified via py_compile (no torch in this environment, so
this is static-only, same as every other change in this file -- real
verification happens on the user's GPU machine). grep confirmed no
remaining references anywhere to _noncanonical_idx, _penalize_indices,
_penalize_noncanonical, or _EXCLUSION_PENALTY outside
tests/archive/test_steepest_descent_JOINT_DESIGN.py (the archived
joint-design test, kept as history, intentionally untouched).

Net effect on sampler behavior: none intended -- same candidate set, same
math, just computed by slicing instead of adding a large negative number
to a fixed-size tensor. The point was removing the -1e6-vs-step_coef*grad
race condition entirely (no numeric constant to be overwhelmed, at any
dt) before running the next sweep at dt=(300,600,1000,1300), which pushes
step_coef well past where the old penalty's safety margin was getting
thin.
